## User Scenarios & Testing *(mandatory)*

> 本特性的"用户"是项目的开发者与维护者。门禁的价值不是单次产出，而是**持续拦截劣化**：每一类检查都是独立可测的切片，可单独落地、单独验证、单独演示。

### User Story 1 - 提交拦截：超限代码进不了仓库（Priority: P1）

开发者提交了超出规模/复杂度约束的代码（如一个 300 行的函数、圈复杂度爆炸的分支嵌套）。`git commit` 被本地钩子拦截，输出精确报告：哪个文件、哪个函数、实测值多少、阈值多少、如何修复。开发者改小后提交顺利通过。

**Why this priority**: 这是用户原始诉求的核心——"commit 的时候要有校验"；没有它，其余门禁都只是记录而非约束。

**Independent Test**: 向仓库注入一个故意超限的变更并尝试提交，应被拦截且报告含位置与数值；恢复正常后提交通过。全程不依赖其他故事。

**Acceptance Scenarios**:

1. **Given** 工作区中一个 Go 函数超过函数长度阈值， **When** `git commit`， **Then** 提交失败，输出含文件路径、函数名、实测行数与阈值的报告。
2. **Given** 前端某个源文件超过文件行数阈值， **When** `git commit`， **Then** 提交失败，报告指明该文件与实测/阈值。
3. **Given** 一个圈复杂度超限的函数（深层嵌套分支）， **When** `git commit`， **Then** 提交失败，报告指明函数位置与复杂度实测值。
4. **Given** 全部改动均合规， **When** `git commit`， **Then** 提交通过，且质量检查环节不显著拖慢提交（秒级而非分钟级）。

---

### User Story 2 - CI 权威门禁：绕过本地的代码进不了主干（Priority: P1）

开发者用 `--no-verify` 绕过本地钩子（或在未安装钩子的机器上提交），PR 推上 GitHub 后 CI 全量校验仍然拦截：同一套阈值在 CI 侧生效，检查报告出现在 CI 日志中，PR 无法合入。

**Why this priority**: 本地钩子可被绕过，CI 是唯一强制点；"git ci 的时候也要有校验"是用户诉求的另一半，两层缺一不可。

**Independent Test**: 推送一个含超限代码的分支触发 CI，对应 job 失败并输出与本地一致口径的报告；修复后 CI 转绿。

**Acceptance Scenarios**:

1. **Given** 含超限代码的 PR， **When** CI 运行， **Then** 质量检查 job 失败，日志含与本地同口径的违规报告。
2. **Given** 违规修复后的新提交， **When** CI 运行， **Then** 质量检查 job 通过。
3. **Given** 同一改动分别在本地与 CI 校验， **When** 对比结论， **Then** 两端结果一致（不存在"本地过 CI 挂"或反之的阈值漂移）。

---

### User Story 3 - 增量与棘轮：规则引入不清算存量（Priority: P1）

门禁规则上线当天，仓库里既有代码不需要任何"为了过检查"的清理：pre-commit 只检查本次变更的文件；CI 全量校验时，存量违规由一份**显式、可评审的基线**豁免。基线随代码改善**只收紧不放松**——修掉一处存量违规就从基线删除对应条目，且任何人不得随意增补条目放大豁免面。

**Why this priority**: 没有增量语义，规则引入第一天就是全量报红，结局只能是被关掉——这是历史上质量门禁失败的第一原因。

**Independent Test**: 对一个含存量违规（基线条目）的文件做与违规无关的修改并提交，应通过；对基线条目之外的增量违规提交，应被拦截。

**Acceptance Scenarios**:

1. **Given** 存量文件含基线登记的违规， **When** 对该文件做无关小改动并提交， **Then** 提交通过（存量不阻塞增量工作）。
2. **Given** 基线未登记的新违规出现在本次变更中， **When** 提交或 CI 运行， **Then** 被拦截。
3. **Given** 有人试图向基线新增条目， **When** 代码评审该改动， **Then** 基线文件的 diff 清晰可见（显式文件，可评审、可追责）。
4. **Given** 存量违规被修复， **When** 移除对应基线条目后运行校验， **Then** 通过；条目移除后再挂回旧违规， **Then** 被拦截（棘轮不可逆）。

---

### User Story 4 - 覆盖率阈值：测试覆盖只能升不能降（Priority: P2）

改动使整体测试覆盖率跌破既定阈值时，CI 失败并展示当前覆盖率与阈值。阈值初始取当前真实基线（不要求先补齐历史欠账），此后随覆盖改善上调、永不因代码增长下调。

**Why this priority**: 覆盖率是最容易被"默默稀释"的质量指标；阈值门禁防的是"新增大量无测试代码摊薄覆盖率"。

**Independent Test**: 注入一段无测试的新代码使覆盖率跌破阈值，CI 应失败并输出两个数值；阈值之上则通过。

**Acceptance Scenarios**:

1. **Given** 当前覆盖率等于阈值， **When** 合入一段显著降低覆盖率的改动， **Then** CI 失败，报告含实测覆盖率与阈值。
2. **Given** 改动同时附带足够的测试使覆盖率不低于阈值， **When** CI 运行， **Then** 通过。
3. **Given** 覆盖率持续改善， **When** 维护者上调阈值， **Then** 新阈值立即生效且此后不再回落。

---

### User Story 5 - 重复代码检测：复制粘贴式增长被拦截（Priority: P2）

一段明显复制粘贴的代码块（超过块数/行数阈值的重复）被检测工具发现并计入门禁，报告给出各重复块的位置。存量重复走基线豁免，新增重复被拦截。

**Why this priority**: 复制粘贴是可维护性劣化的主要来源之一；该检查与规模/复杂度互补（短而重复的代码不会触发行数/复杂度阈值）。

**Independent Test**: 在新增代码中粘贴一段足够长的既有代码块，校验应失败并给出两处位置；等量原创代码不受影响。

**Acceptance Scenarios**:

1. **Given** 新增代码与既有代码存在超过阈值的重复块， **When** 校验运行， **Then** 失败，报告列出全部重复位置。
2. **Given** 基线登记的存量重复， **When** 未触碰这些代码， **Then** 不阻塞提交与 CI。
3. **Given** 小于阈值的巧合相似（惯用写法、样板代码）， **When** 校验运行， **Then** 不误报。

---

### User Story 6 - 依赖漏洞扫描：已知漏洞不进主干（Priority: P2）

CI 定期扫描 Go 与前端依赖中的已知安全漏洞；存在**可触达**（被实际调用链使用）的高危漏洞时 CI 失败，报告列出漏洞编号、涉及依赖与修复建议（升级版本）。仅存在而未被使用的漏洞给出警告但不阻塞。

**Why this priority**: 安全基线（宪法原则 VI）要求不降级；依赖漏洞是外部输入，无法靠代码评审发现。

**Independent Test**: 向依赖清单注入一个已知漏洞版本，CI 应失败并指明漏洞；恢复后转绿。

**Acceptance Scenarios**:

1. **Given** 依赖中存在已知且可触达的高危漏洞， **When** CI 运行， **Then** 失败，报告含漏洞标识与涉及依赖。
2. **Given** 漏洞存在于依赖中但调用链未触达， **When** CI 运行， **Then** 输出警告不阻塞，留待升级消解。
3. **Given** 干净的依赖树， **When** CI 运行， **Then** 扫描步骤通过且输出可读的"未发现漏洞"结论。

---

### User Story 7 - 死代码检测：腐化存量可见、增量清零（Priority: P3）

未被引用的导出、依赖与文件被检测工具发现并计入门禁报告。存量死代码登记基线（可逐步清理），新增死代码被拦截。报告帮助维护者决定清理对象。

**Why this priority**: 死代码是低危但持续累积的债；放在 P3 因为其拦截价值低于规模/复杂度/覆盖率，误报治理成本略高。

**Independent Test**: 新增一个无任何引用的导出/依赖，校验应失败并指明位置；基线条目不阻塞。

**Acceptance Scenarios**:

1. **Given** 本次变更新增了仓库内无引用的导出， **When** 校验运行， **Then** 拦截并指明位置。
2. **Given** 基线登记的存量死代码， **When** 未触碰， **Then** 不阻塞。
3. **Given** 有明确外部契约理由保留的导出（如被 embed/反射引用）， **When** 配置豁免， **Then** 有显式、可评审的豁免机制而非删除检查。

### Edge Cases

- **生成物与第三方代码**：嵌入的前端构建产物、vendor、锁文件、specs/ 过程文档等不属于质量约束对象，MUST 可配置排除，否则门禁第一天就会误报。
- **工具未安装**：本地未装检查工具时，MUST 快速失败并给出安装指引（沿用 commitlint 的 `npx --no` 本地优先、快速失败惯例），MUST NOT 静默跳过造成"假绿"。
- **平台差异**：本地校验脚本 MUST 跨平台可用（macOS/Linux/Windows git-bash 与 cmd），沿用 Makefile 既有跨平台约定；无法跨平台的检查 MUST 只放 CI 并在文档标注。
- **提交速度**：pre-commit 增量校验 MUST 保持秒级；全量校验只属于 CI。
- **误报出口**：每类检查 MUST 有文档化的、显式的单点豁免机制（工具原生注释标记或豁免清单），供极少数合理例外使用；豁免 MUST 在评审中可见。
- **基线失真**：若基线条目对应的违规实际已被修复，MUST 允许删除条目（棘轮向下）；若代码回退使基线条目复活，MUST 被拦截（棘轮不可逆）。
- **检查工具自身的版本漂移**：门禁工具版本 MUST 固定（锁版本），避免工具升级悄悄改变规则口径导致 CI 突然变红。

## Requirements *(mandatory)*

### Functional Requirements

**双层执行点**

- **FR-001**: 质量校验 MUST 在两个执行点强制生效：本地 `git commit`（pre-commit 钩子，沿用现有 lefthook，不引入 husky）与 GitHub Actions CI（push/PR 触发）。
- **FR-002**: 两层校验 MUST 复用同一套 make 目标与同一份阈值配置（单一真值），MUST NOT 出现本地与 CI 阈值漂移。

**校验范围（规模与复杂度，核心）**

- **FR-003**: 门禁 MUST 校验单文件行数上限（Go 与前端源码均适用）。
- **FR-004**: 门禁 MUST 校验单函数长度上限。
- **FR-005**: 门禁 MUST 校验函数圈复杂度或认知复杂度上限（至少其一）。
- **FR-006**: 门禁 MUST 校验单行长度上限与函数参数个数上限（规模约束的配套项）。
- **FR-007**: 违规报告 MUST 包含：文件路径、函数/位置标识、实测值、阈值；MUST 能让开发者不经翻代码即可定位问题。

**增量与基线（棘轮）**

- **FR-008**: pre-commit MUST 只校验本次变更的文件（增量门禁）；存量违规 MUST NOT 阻塞与其无关的提交。
- **FR-009**: CI MUST 全量校验，存量违规 MUST 经显式基线豁免；基线是提交在仓库中的文件，其变更在评审中可见。
- **FR-010**: 基线 MUST 满足棘轮语义：条目只允许移除（修复后）或随阈值收紧而减少，MUST NOT 允许无理由新增；绕过本地钩子的增量违规 MUST 在 CI 被拦截。

**增量扩展项（已确认纳入）**

- **FR-011**: 覆盖率阈值门禁：整体测试覆盖率 MUST 设下限阈值；跌破时 CI 失败并输出实测值与阈值；阈值按当前基线起步，只升不降。
- **FR-012**: 重复代码检测：超过阈值的重复代码块 MUST 被检测并计入门禁（Go 与前端源码），报告列出各块位置；存量走基线。
- **FR-013**: 依赖漏洞扫描：CI MUST 扫描 Go 与前端依赖的已知漏洞；可触达的高危漏洞 MUST 使 CI 失败；未触达漏洞降级为警告。
- **FR-014**: 死代码检测：未被引用的导出与依赖 MUST 被检测并计入门禁（存量走基线）；MUST 提供显式豁免机制应对有契约理由的保留。

**工程整合**

- **FR-015**: 全部新检查 MUST 纳入 `make check` 统一入口；既有检查（gofmt/vet/mod-tidy、前端 typecheck/lint/format、scripts-check、presets-lint）MUST 全部保留且不受影响。
- **FR-016**: 生成物、第三方与过程文档 MUST 可配置排除在门禁外（排除清单提交在仓库中、可评审）。
- **FR-017**: 检查工具版本 MUST 固定（本地与 CI 同版本），工具升级属于显式流程决策。
- **FR-018**: 每类检查 MUST 配套文档：检查什么、阈值多少、如何本地运行、如何豁免单点、如何修基线。
- **FR-019**: 行为变更 MUST 同步 docs/acceptance-tests.md（宪法原则 V）；门禁阈值与基线的维护规则 MUST 回流 docs/（宪法原则 VII）。

### Key Entities *(include if feature involves data)*

- **阈值配置**：所有门禁阈值的单一真值来源（文件形式，提交在仓库）；本地与 CI 读取同一份。
- **质量基线**：存量违规的显式快照（文件形式），按检查类别组织；条目含位置标识；棘轮语义的载体。
- **门禁报告**：校验失败时的人类可读输出；含位置、实测值、阈值、修复指引。
- **排除清单**：不参与门禁的路径/文件模式集合；提交在仓库、可评审。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 注入验证——刻意注入的每类违规（超限函数/文件/复杂度/重复/死代码/漏洞依赖）100% 被本地提交或 CI 至少一层拦截，且报告含定位信息。
- **SC-002**: 零清算上线——门禁规则合入当天，除基线文件与配置外，MUST NOT 需要修改任何既有业务代码即可全绿。
- **SC-003**: 两端一致——同一改动在本地与 CI 的校验结论不一致率为 0（同一阈值配置、同一工具版本）。
- **SC-004**: 提交不减速——合规改动的 pre-commit 中，新增质量检查环节耗时 ≤10 秒（增量校验）。
- **SC-005**: 棘轮生效——基线条目数随修复单调不增；任何使既有基线违规复活的改动都被拦截（可用回退实验验证）。
- **SC-006**: 可观测——CI 输出中可直接读到：覆盖率数值、重复块计数、漏洞计数、死代码计数等关键度量。

## Assumptions

- **工具选型**（需求 R12 已确认）：Go 侧以 golangci-lint 聚合器承载规模/复杂度/重复/死代码检查；前端沿用现有 ESLint 体系开启对应规则；跨语言重复检测与前端死代码检测引入轻量工具；覆盖率阈值由现有测试框架配置承载。具体版本与配置在 plan 阶段定案。
- **阈值取值**（Q22 已定策略）：plan 阶段先测量当前代码基线，阈值取"基线友好"的宽松值起步，运行稳定后按棘轮逐步收紧；本 spec 不预设具体数字。
- **基线形态**：假定基线以机器可读的文本文件随代码提交（可 diff、可评审）；其具体格式（工具原生格式 vs 自定义格式）在 plan 阶段定。
- **执行成本**：假定 CI 校验加入现有 lint job（不新建矩阵维度）；本地开发者已在 `npm install` + Go 工具链就绪的环境工作（与现有 pre-commit 前提一致）。
- **范围边界**：本特性只加"校验"，不改任何业务行为；不引入重量级质量平台（SonarQube 等，R12 非目标）；架构依赖方向约束（depguard 类）留待后续版本。
